# 代码分类与阅读指南

## 当前默认助餐场景

10月26日运营扩展见`meal_ops.py`、`MealOperations.tsx`：登记排班、候选冲突、资源对比、待办和操作卡；`meal_routes.py`接受动作在写事务内复查人员占用。`collect_panyu_evidence.py`交叉核对两份官方历史名单，报告在`app/data/research/panyu-public-evidence.json`，保留冲突且不推断当前供给。

2026-10-24起默认进入广州番禺助餐接力。先读`app/backend/src/anxin/meal_domain.py`（字段与约束）、`meal_routes.py`（核实/状态机/异常重排），再读`app/apps/web/src/MealWorkbench.tsx`与`mealApi.ts`。`Workspaces.tsx`保留旧复诊入口，两个场景不覆盖彼此记录。

官方历史名单在`app/data/seeds/panyu_resources.json`，固定页面导入器为`app/scripts/import_panyu_resources.py`；当日价格、营业与代取资格必须人工核实。演示与试点用途创建后不可互改，新增MealCase表和事件不覆盖原有需求/草案。[操作与验收](../app/docs/番禺助餐场景_实施与验收_20261024.md)。

## 原复诊场景阅读顺序

1. 先看app/backend/src/anxin/domain.py，了解需求字段、未知值和演示输入。
2. 看model_gateway.py，了解真实调用、模型参数适配、原文证据及最多一次修正。
3. 看planning.py，了解确定性约束、事项模板、依赖及草案边界。
4. 看storage.py和main.py，了解数据事务、版本检查及HTTP入口。
5. 看app/apps/web/src/api.ts和App.tsx，了解页面如何读写服务端权威状态。
6. 最后看后端tests及前端e2e，确认每个行为怎样被验证。

## 后端模块职责

| 文件 | 负责什么 | 重要约定 |
|---|---|---|
| config.py | 从本机环境与.env读取配置 | 密钥不返回前端；默认数据库位于runtime |
| domain.py | Pydantic输入与需求Schema、缺项清单 | 未知值为null；NA等原文字面值不自动抹除 |
| model_gateway.py | 模型HTTP适配、JSON解析及原文依据核对 | 输出无依据则拒绝；最多一次修正，共享超时 |
| planning.py | 时段与预算规则、模板展开、事项DAG | 草案不产生预约；模型不决定规则是否通过 |
| storage.py | Need、Resource、PlanDraft、Event及会话 | 数据在SQLite持久化；事件和对象变更同事务 |
| main.py | API、错误处理、静态页面与用例连接 | 编辑采用expected_version；旧模型结果不覆盖新编辑 |

## 前端模块职责

| 文件 | 职责 |
|---|---|
| src/main.tsx | React入口、Ant Design中文与主题 |
| src/api.ts | 共享类型、HTTP请求封装、时间与来源显示 |
| src/App.tsx | 需求输入、字段核对、时间线、约束、资源、事件与回读 |
| src/styles.css | 三栏布局、状态配色、窄屏堆叠 |
| vite.config.ts | 开发期/api代理，避免前端接触供应商密钥 |
| playwright.config.ts | 浏览器回归配置，优先检测本机Edge |

App.tsx当前按状态、读写动作、字段编辑、工作台视图分段注释；后续页面扩展时再按业务组件拆分，避免本轮整理同时改变交互行为。

## 数据流

```text
用户原文
  → POST /api/needs
  → 真实模型或明确标记的演示／手工模式
  → Pydantic结构校验 + 原文证据校验
  → 用户核对与PATCH（expected_version）
  → POST /api/needs/{id}/plan-drafts
  → 匹配资料 + 确定性规则 + 无环依赖检查
  → SQLite保存草案与事件
  → 页面回读／刷新恢复
```

## 注释约定

- 模块文档字符串说明职责和输入输出，函数注释重点解释业务原因与边界。
- 对版本冲突、未知费用、证据校验、草案不等于预约等关键规则保留中文说明。
- 不给明显赋值逐行加注释，不把未完成的规划描述为已实现。
- 密钥、真实家庭资料及完整模型请求不写进注释和运行日志。

## 测试与工具

后端test_workflow.py覆盖接口和业务链路；test_model_profiles.py覆盖模型参数、输出截断、非法依据与修正次数。它们只使用临时数据库或内存HTTP模拟。

test_acceptance.py补充A03缺项、A05混合报价、A06时间版本、A08异常消息及手工接续、A10响应边界检查，仍不请求真实供应商。

前端workbench.spec.ts覆盖可交互流程与模拟故障界面；live-result.spec.ts仅回读已存在的真实验收记录，没有该记录时跳过，不自动请求供应商。scripts/verify_live.py会主动发起单样例真实模型验收，可能产生初次请求与一次修正调用。

scripts/verify_acceptance.py默认检查健康、独立API进程重启和文件凭证；带--live时实际执行三个合成输入的模型验收，可能产生费用。结果保存在runtime，字段漏提会如实返回失败，不属于完整A01—A10的独立替代品。

scripts/check_staged.py检查Git暂存内容，阻止依赖目录、运行数据或可识别凭证进入提交；结果只包含文件名，不打印凭证。

## A02整改后的新增模块

- backend/src/anxin/extraction_checks.py：确定性遗漏/冲突检查、越权指令句隔离及关键引用支持检查；只拒绝或报告问题，不代填模型结果。
- backend/src/anxin/resources.py与data/seeds/public_resources.json：公开来源校验、地区范围、时效提示；当前营业和价格不因有公开报道而被确认。
- apps/web/src/components/ResourceCard.tsx：演示、公开地点、官方查询与说明分别标记，来源链接仅供用户主动查看。
- backend/tests/test_extraction_checks.py与test_resources_transactions.py：遗漏修正、注入、目录保护、并发生成和事务回滚。
- storage.immediate_session是唯一BEGIN IMMEDIATE入口；新建会话与统一提交/回滚由它负责，业务接口不再手动嵌套BEGIN。

verify_acceptance.py的--live-injection会追加真实注入合成输入，--case injection可只复测这一条；多例默认间隔22秒，429直接返回，不自动重试。实际边界与首次失败见app/docs/A02整改与资源接入记录_20261023.md。
